# The other column: real widgets, over a bridge

`nodegui` hands you Qt. `node-gtk` hands you GTK. Both give you widgets a
native developer would recognise — the platform's own look, its own
accessibility, its own decades of work — and you implemented none of it.

That is a real win, and it is the thing this project has to work hardest to
earn.

^^^

The cost is the boundary, and it is in a different place:

- **Your tree is not the widget tree.** It is a script that *drives* one.
  Every prop crosses a language boundary to get there
- You inherit their **threading model**, their **event loop** and their
  **build story** — Qt or GTK has to be on the machine, and `node-gyp` has to
  have worked
- And the layer you most want to change is the layer you cannot reach

^^^

So: both columns are a **boundary**. One puts it between your UI and the
desktop; the other puts it between your code and the widgets.

^^^

The question this talk is: **what if there were no boundary?** What if the
layout, the text, the painting and the protocol were all just JavaScript you
could open and read?

And the answer is that it is a **lot** of work — work the browser and Qt had
both already done for you, which is exactly why they are reasonable answers.
